# App Integration — Detailed Dev Log

**Branch:** `feature/app-integration` (created 2026-10-02 from `main`)
**Goal:** make this backend serve the Rentlo Flutter app (`CodeBySushant/Renterp-frontend`) end to end — authentication, the data the app screens need, and the gaps found while building the app.
**Status:** In progress. All work stays on this branch and goes to `main` as one pull request when complete.

---

## Why a branch

`main` is the project owner's work and is kept as it is. Every change for the
app lands here first, follows the conventions already set in `DEVLOG.md`
(live Postgres testing, Postman collection + `TEST_RESULTS.md` per controller,
a `DEVLOG_<CONTROLLER>.md` per controller, FK existence checks in services,
Edge Case Register read before the service layer), and is reviewed in one PR.

Running record of the branch:

| File | What it holds |
|---|---|
| this file | Why each change was made, decisions, open items — newest entry at the bottom |
| `DEVLOG.md` → "Phase 6 — App integration" | Short summary per task, as for earlier phases |
| `docs/BRANCH_COMMITS.md` | Every commit on this branch, generated by `scripts/update_branch_log.ps1` |
| `docs/PR_APP_INTEGRATION.md` | The pull-request description, kept current as work lands |

## Starting point (audit of `main`, 2026-10-02)

Built and tested on `main`: users, properties (+ all policy settings),
property access, floors/rooms, charge templates, meters (+ coverage, infra
scope), readings (+ corrections, replacement, coverage events), tenancy
(profiles, KYC, join requests, memberships, room assignments, blocks), tenant
finance, billing (tariffs, runs, bills, corrections, adjustments, async).

Gaps that block or limit the app:

| # | Gap | Notes |
|---|---|---|
| G1 | **No authentication.** `SecurityConfig` is `permitAll()`; no auth controller; `otp_attempts` and `user_sessions` exist but are unused; no JWT library; `JWT_SECRET` is in `.env` but unread; `users` has no email or password. | The app's login/sign-up contract: frontend `docs/BACKEND-AUTH-CONTRACT.md`. |
| G2 | **Hindi rejected.** `CreateUserRequest`/`UpdateUserRequest` accept `en\|ne`; `tenant_profiles` has `CHECK (preferred_language IN ('en','ne'))`. | The app ships English, Hindi, Nepali. |
| G3 | **Error mapping.** No 401/403, 410 or 429; malformed JSON and bad path UUIDs return 500. | The app maps 401/404/409/410/429 to specific messages. |
| G4 | **Screen-shaped reads missing.** Dashboard aggregates, per-property counts, tenant rows with room names, owner search. | App currently composes several calls or shows "—". |
| G5 | **Domains not built.** Payments (Khalti/eSewa), vacancy/move-out/settlement, room operations, notifications, file upload, reports. | Scope to be agreed before building. |
| G6 | **Tenant requests.** The app has maintenance / room-change / vacate / custom requests; `RENT_ERP_CONTEXT.md` lists maintenance requests as out of scope for beta. | Decision needed. |
| G7 | **Docs drift.** `RENT_ERP_CONTEXT.md` still names React Native and two languages; `.gitignore` carries React Native `frontend/` entries; `.env.example` lists services no code reads. | Fix alongside the related work. |

Order and scope of the work are agreed task by task; each task gets an entry below.

### [2026-10-02] G1 + G2 + G3: authentication, authorization foundation, Hindi, error codes

- **Auth (G1):** `AuthController` with the eight endpoints the app's auth screens call, sessions in `user_sessions`, rotated refresh tokens, OTP and password limits, dev-only OTP logging. Detail and decisions: `DEVLOG_AUTH.md`.
- **Authorization:** `AccessGuard`, used by services. This pass covers users, properties and property access; the remaining domains follow (structure, meters, readings, tenancy, finance, billing).
- **Hindi (G2):** V13 allows `hi` in `users` and `tenant_profiles`; DTO patterns updated.
- **Errors (G3):** `ApiException` (status + code), every error body carries `code`; 400 for malformed input, 409 for constraint violations, 401/403/410/429/503 where they apply.
- **Decisions:** JWT signed with the JDK (no new dependency); `AUTH_ENFORCED` defaults to true and exists only so the owner's Postman collections still run locally; the app's `ownerUserId` query parameter is ignored for non-admins.

### [2026-10-02] Billing screens on the existing billing runs

No new endpoints: the app now drives the existing billing-run API. Create Bill (live) picks the period from the property's billing day (current or previous window), asks only for the figures the property's electricity / water modes need (NEA total, per-tenant fixed amount, rate per unit, KUKL / boring totals), creates a DRAFT with an Idempotency-Key (a retry replays the same run; a second run for the month is refused), reopens an existing draft or shows a sent month instead of making another, reviews per-tenant bills, then sends (confirm) or discards (cancel).
